最初にプロジェクトへ小さな機能を追加しましたが、大きな変更には、より堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるように設計されており、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue を使って新機能を作成し、コードが有効で機能が期待どおりに動作することを確認して、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションや pull request (PR) を使用しますが、ここでは中心となる概念に集中できるように手順を短縮します。

このレッスンでは、次の内容を学習します。

- GitHub Issue から新しいエージェントセッションを開始する。
- **Plan** モードで要件を定義する。
- **Autopilot** モードを使用して新機能を実装する。
- コードをレビューする。
- ブラウザーキャンバスで機能を手動検証する。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、Model Context Protocol (MCP) による検証を追加し、品質保証 (QA) エージェントを作成して、機能の pull request (PR) を作成します。

## シナリオ

Tailspin Toys のカタログが充実し、訪問者がカテゴリーとパブリッシャーでゲームを絞り込める機能が必要になりました。バックログの Issue に機能は記載されていますが、カテゴリーの組み合わせ方などはコーディング前に合意が必要です。Plan モードで決定事項を整理してから、Autopilot による範囲を限定した実装を承認します。

## 背景

人工知能 (AI) を活用したコーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のようなフローに従います。

1. 必要な作業の詳細が記載された Issue を開く。
2. 構築する内容の計画を作成する。
3. コードを構築してレビューする。
4. テストを実行してコードを検証する。
5. 新機能を手動で検証する。
6. pull request (PR) を作成する。
7. コードのレビューと継続的インテグレーション (CI) プロセスが成功したら、コードをマージする。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを変形したものです。

この標準的なアプローチを守ることで、AI が生成したコードが定められた要件を満たし、人間が作成したコードと同じ審査プロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントの自律性を制御します。プロンプトフィールド下のドロップダウンから設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが共同で作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。計画を実行する前に内容をレビューして承認します。
- **Autopilot**: エージェントが完全に自律して作業し、入力を待たずにコードの作成、テストの実行、反復を行います。

Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

Issue と最新の `main` に関連付けたセッションを使うと、フィルター機能の作業を既存のバックログと一緒に追跡できます。

1. 星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。
2. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに用意された既存の Issue です。新たに作成する必要はありません。
3. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

4. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

5. Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションでは動作しない場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして持っています。計画を依頼し、Issue の受け入れ条件に照らし合わせて確認します。

1. 次のプロンプトを送信します。

    ```plaintext
    Build this feature.
    ```

2. Copilot の質問に回答し、Issue の受け入れ条件と計画を照らし合わせます。カテゴリーとパブリッシャーによる絞り込み、アクセシビリティに配慮したコントロール、データアクセスの変更、テストが含まれていることを確認します。
3. 複数のカテゴリーをどのように組み合わせるか、一致するゲームがない場合にどうなるかなど、不明確な動作について話し合います。
4. 計画に、プロジェクトの既存ツールを使った lint、単体テスト、エンドツーエンド (E2E) テスト、型チェックが含まれていることを確認します。フィルター機能の実装とテストに範囲を絞ります。品質ワークフローを完了するまでは PR を作成しません。
5. 計画の修正を承認前に依頼し、後の検証に使えるよう Issue の URL と合意した補足事項を控えておきます。

## Autopilot を明示的に承認する

実装がすぐに始まる場合があるため、計画を確認してから承認し、意図したモードで作業が進むことを確かめます。

1. **Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。
2. 承認しただけでモードが切り替わると思い込まず、モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を開始し、計画に沿ってコードを生成し、テストを実行しながら反復して進めます。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があります。

3. Copilot から依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、他のコードと同じようにマージ前のレビューが必要です。コードをレビューし、サイトを実行して問題がないことを確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリーとパブリッシャーの組み合わせも含め、結果を Issue と承認した補足事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、単体テスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できます。テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

ブラウザーキャンバスで実際に操作すると、フィルター機能が計画と Issue の要件を満たすか確かめられます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリーを選択し、結果がそのカテゴリーに一致することを確認します。フィルターを解除してからパブリッシャーを選択し、結果がそのパブリッシャーに一致することを確認します。
4. カテゴリーとパブリッシャーのフィルターを組み合わせ、結果を Issue と承認済みの計画に照らし合わせます。複数カテゴリーがサポートされる場合は、合意した組み合わせ方も検証します。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けてセッションを保持する

次のレッスンでは、フィルター機能と品質ワークフローを引き続き同じ作業場所で進めます。

1. ここではフィルター機能の PR を作成またはマージしません。カスタム指示、スキル、QA の改善を続け、レッスン 8 でまとめた PR を作成してマージします。
2. 開発サーバーを停止した後も、同じセッション、worktree、ブランチを保持します。
3. セッションはアイドル状態のままにして構いません。次のレッスンで同じセッションに戻ります。
